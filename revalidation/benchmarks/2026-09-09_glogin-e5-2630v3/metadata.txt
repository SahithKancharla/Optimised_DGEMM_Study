WHAT THIS RUN IS AND ISN'T:
- IS: a real, executed, end-to-end sanity check that the (now-fixed) code
  builds and runs correctly across Serial/Parallel/AVX2 code paths on real,
  different hardware than the paper used, and a rough directional check of
  whether the paper's qualitative performance claims (unrolling helps, blocking
  helps, pure Strassen is bad under parallelism, hybrid Strassen wins at medium
  sizes, etc.) reproduce.
- IS NOT: a substitute for re-running the paper's actual benchmark suite on
  the Xeon Gold 5218 (32-core, AVX-512) the paper was written against. No
  AVX-512 hardware was available for this session (see conversation history),
  so the "AVX2" numbers here use avx/kernel_avx2.c and avx/strassen_avx2.c,
  which are correctness-verified ports but were NOT independently
  performance-tuned for AVX2 the way the original kernel.c/strassen.c were
  tuned for AVX-512 on Cascade Lake -- do not treat the AVX2 absolute
  numbers, or the blocked-vs-Strassen-AVX2 comparison, as representative of
  what the AVX-512 build would show. The correctness of the fixes is the
  reliable takeaway; the exact performance crossover points are not.
- Matrix data uses the paper's own A[i][j]=i+j, B[i][j]=i*j pattern (matching
  what Serial/Parallel/main.c and avx/main.c generate), NOT the asymmetric
  data used during correctness testing -- this run is about timing, not
  correctness (correctness was separately and exhaustively verified; see
  ../correctness/).
